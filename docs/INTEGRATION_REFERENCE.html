NEXUS Integration Reference

NEXUS is a belief substrate: your workflow sends it questions and facts, it answers from an auditable store, and every answer leaves a sealed lineage record you can verify later. This page covers the write path (ask, confirm outcomes, install policy, assert facts, pin a model, archive a duplicate) and the read path (lineage, provenance, verification, the governance budget).

1Basics

  • Base URL — the NEXUS host, default http://localhost:8000. Interactive OpenAPI at /docs.
  • Auth — every write, and the whole lineage / provenance / verification / budget / refusals read path, requires Authorization: Bearer <token> (the server's NEXUS_API_TOKEN, or the per-process session token printed at startup). Missing or wrong: 401 {"detail": "unauthorized"}. §5 lists every route with its auth posture.
  • Proxy mode (W4) — with NEXUS_AUTH_MODE=proxy the bearer token is no credential. Every request but /health and /healthz must come from a loopback peer (the identity proxy beside NEXUS) carrying the identity header (NEXUS_IDENTITY_HEADER, default Tailscale-User-Login) exactly once: 401 otherwise; 403 when the process has no owner set (owner not set) or the login is not its owner's. The login is compared exactly: only the spaces and tabs around it are trimmed. An unsafe request from a browser (any method but GET, HEAD and OPTIONS) must be same-origin: one whose Sec-Fetch-Site is present and is not same-origin, or one that carries Origin and no Sec-Fetch-Site, is 403. A client that is not a browser sends neither header and is not refused. GET /whoami says the mode and the login. The login is each record's accountable_identity, with identity_mechanism: "proxy".
  • Content type — JSON bodies. The one exception: /chat responds with text/event-stream (§3.1).
Gotcha · two 422 shapes A schema error (missing or mistyped field) returns FastAPI's shape — {"detail": [{"type": "missing", "loc": ["body", "confirmed"], "msg": "Field required", …}]}. A domain refusal returns a named error — {"error": "scope_too_long", …}. Branch on error when present; fall back to detail.

Two other status codes carry named errors: 409 for conflicts (version_reused, ambiguous archive target) and 503 {"error": "provider_unreachable", …} when the model backend is down (§3.5). Neither is a 422.

2Scope — read this before anything else

scope is how your workflow tells NEXUS which process step (or programme — the value is opaque, structure it as you wish, e.g. "trial-alpha/step-3") a record belongs to.

Unsupplied scope records as the literal string "default" — it is never null, and NEXUS never infers it from message content, session, or timing. If you did not send it, it was not recorded; there is no retroactive scoping. Whitespace-only counts as unsupplied.

  • Carried by three endpoints: POST /chat, POST /outcome/confirm, POST /governance/envelope/confirm. Optional string on each.
  • Length cap: 256 characters. Longer → 422 {"error": "scope_too_long", "max_chars": 256, "got": n}. It is the first check each of the three endpoints makes, before the Law 3 gate.
  • A stated scope is sealed into the record's hash (tamper-evident). Records from before the field existed read "default" forever — GET /cortex/stats → scope.recordable_since is the timestamp that makes the two cases distinguishable.
  • POST /kb/assert/confirm and POST /kb/dedup/confirm deliberately do not take scope: they act on beliefs, and beliefs are unscoped by design.

Turns a stated sentence into a stored belief — source human_assertion, evidence class asserted: the slowest-decaying class in the store, and the one the default envelope cannot move.

{"sentence": "TAK-441 is metabolized by CYP3A4.", "confirmed": true}

Gotcha · a 200 may store nothing A sentence that cannot be shaped into a subject–relation–object triple returns 200 with "shaped": false, "stored": 0, "beliefs": [] and a hint — deliberately, so you learn the claim is unstorable rather than getting silence. Always check stored. An empty sentence is 422 empty_sentence; a gate refusal appears inside beliefs as {"refused": "…", "subject": …} and is not counted. confirmed: false is 422 with event_id and recorded: true (§4.6); the sentence is not stored on the ledger, only a digest of the request.

Relations are normalised on ingest (is → is_a, and other aliases), and as_parsed carries the triple as the shaper read it, named separately. The assertion offer on the /chat stream (kb_pressure_alert{type: "assertion"}.triples[]) has the same shape: stored form under the plain keys, as_parsed beside it. No scope field here (§2).

POST/model/overridebearer required

Pin the answering model. DELETE /model/override clears it. Extraction always uses its own model regardless.

Request {"model": "<role or raw model name>", "lock": false}. lock: false pins the next turn only and clears at its end; lock: true persists until the DELETE.

  • A role needs no backend to be pinned: code | extraction | general | multimodal | primary | reasoning. Which roles can answer is derived from the model registry's capability declarations, not listed: embed resolves to a model that declares only embedding, so it is refused — 422 {"error": "model_cannot_answer", "model": "embed", "resolved_model": "nomic-embed-text", "capabilities": ["embedding"], "valid": […], "hint"}. extraction stays pinnable because its model also declares general reasoning.
  • A raw model name is validated against the backend's installed list: unknown → 422 {"error": "unknown_model", "model", "hint"}; backend down → 503 {"error": "provider_unreachable", "backend": "ollama", "detail": "ConnectionRefusedError: …", "hint": "…"} — a named error, never a raw 500. A raw name the registry knows (same tag, or the same base before the colon) gets the same model_cannot_answer check; a tag the registry has never heard of is accepted as experimental.

Response 200: {"override_active": true, "resolved_model": "qwen3.5:9b-q4_K_M", "locked": false}; DELETE → {"override_active": false}. GET /model/status (open) shows active_model, override, locked, available (empty when the backend is down), backend.

POST/kb/dedup/confirmbearer required

Archive one side of a near-duplicate pair. Candidates come from GET /kb/dedup/pending (open), which carries the example body.

Body: the two triples (subject_a / relation_a / object_a, _b likewise), keep: "a" | "b", confirmed: true, optional source_a / source_b naming the evidence class to archive, and optional actor_id ("operator"), actor_role, actor_source with the same closed vocabularies as /outcome/confirm — refused as 422 {"error": "unknown_actor_role", "role", "valid": […]} (the permitted list is valid on every route; a vocabulary refusal is a client error and is not recorded). confirmed: false is recorded on the refusal ledger with the stated actor (§4.6).

  • Archiving never deletes: the row stays, archived: true, archive_reason: "dedup", visible on /lineage/{id}.
  • If the triple exists under several sources and none was named: 409 {"error": "ambiguous archive target", "sources": […], "hint", "event_id", "recorded": true} — recorded on the refusal ledger (§4.6): the system could have archived both and declined to guess which copy you judged.
  • Response 200: {"archived": [s, r, o], "kept": "a", "rows_archived": 1, "tier": 4, "tier_deprecated": true}.
  • Every archival writes an archival act (who, when, why, which direction) to the ledger in §4.6.

Commit now, reveal later (W9): a salted commitment to a note you supply, sealed by the next seal, so you can later prove you held it on that date without disclosing it until you choose.

6The minimal integration, end to end

  1. Turn. POST /chat with message and your scope. Stream the SSE from the first byte; render token frames; on done, store lineage_id against your process step, and keep citation_forecast only if you are measuring.
  2. Later, the world answers. POST /outcome/confirm with references: {"lineage_id": …}, direction, the same scope, actor_role: "source_system" if a system is reporting, and confirmed: true. Expect applied: [] until a policy is installed.
  3. When anyone asks why. GET /lineage/{id} for what the answer rested on, GET /belief/{id}/provenance for why the evidence weighs what it does, GET /lineage/verify and GET /governance/verify to prove none of it was altered, and GET /governance/budget for how much the policy let anyone move.

8. NEXUS as an MCP server — the mcp contract, version 5 (MCP-2; W0b; W6; W9; W10b)

python -m backend.mcp serves NEXUS over stdio to an MCP client (one process per person, their own store). The HTTP app is never constructed and the bearer token has no role; the tool layer names no transport, so the SDK's streamable-HTTP transport stays reachable for a later runner. SDK mcp>=2.3,<3.

The turn is split at the model call. nexus_retrieve runs the first half of the loop (prepare_turn) and returns the block and a retrieval_id; the client's model answers; nexus_record runs the second half (complete_turn) on the answer the client sent and seals the record. Pinned: the two-call turn equals the one-call turn, and the console path is byte for byte against the pre-split base (tests/test_mcp2_build.py).

Coverage. Complete for every turn the client recorded; retrievals without a record are counted; turns with neither are not visible to NEXUS. Learning. Frozen is MCP mode's code default; NEXUS_LEARNING=live is the opt-in; the from-date is the first run on the store. The console's default is unchanged. Records seal in the MCP process: the governance seal runs alone on a housekeeping tick, never the idle cycle's learning passes.

Configuration (environment or .env): NEXUS_MCP_OWNER, NEXUS_MCP_DATA_ROOT (an absolute folder holding the store and the three logs; unset, empty, relative or an unexpanded ${...}, the per-user application-data folder, never the working directory: W2), NEXUS_MCP_HANDLE_TIMEOUT, NEXUS_LEARNING, NEXUS_KEEP_REQUESTS (W0b; whether the block is kept). One process opens a store (W2): a second, in MCP mode or the console, is refused with “this store is open in another NEXUS process (pid N, since T)” and exit 7, having opened nothing. 9. Verifying a credential, a reveal or an action: nexus-verify (W9, W10b)

scripts/nexus_verify.py is one file with no NEXUS import (stdlib only), so a stranger can check a credential with no store and no install; release.yml also packages it as a binary for Linux, Windows and macOS.

nexus-verify credential.json --identity identity.json      # pinned to the instance's GET /identity body
nexus-verify credential.json --key <64 hex>                # or one public key, active at any time
nexus-verify --reveal receipt.json --content note.txt --salt <64 hex> --identity identity.json
nexus-verify --action action.json --identity identity.json   # a governed action's receipt (W10b)
nexus-verify ... --tsa-cert authority.pem                  # also check the RFC 3161 anchors
nexus-verify ... --json                                    # the result as JSON

It checks each disclosed value against its commitment, the commitment root, the proof to the block's root (RFC 9162), the block's hash, the instance's Ed25519 signature (RFC 8032) by a pinned key within that key's period, and, with --tsa-cert, each anchor's token (RSA PKCS#1 v1.5 or ECDSA P-256/384/521). Exit 0 prints nexus-verify: VERIFIED and each disclosed field; exit 1 prints FAIL <name>: … for every failure (disclosure_mismatch, commitments_mismatch, unsalted_hash, root_mismatch, root_not_sealed, block_hash_mismatch, signature_invalid, signature_outside_key_period, unsigned, key_unpinned, reveal_mismatch, action_mismatch, anchor_invalid, …); exit 2 is input it cannot read. --action checks the fields against the record hash, its path to the block's action root, the block's hash and signature, and a disclosed accountable identity against its commitment. A run given neither --identity nor --key fails key_unpinned: a document's own key list proves nothing. A note is read exactly as UTF-8, line endings kept: a reveal of the same text with other line endings fails.
