# NEXUS — Architecture

*For an engineering team assessing the system's structure and what integrating it would involve. Derived from the code as it stands; every structural claim below traces to a module in the repository. Statements that are inference rather than observation are marked as such. Deliberately omitted throughout: tunable parameters (thresholds, decay rates, dimensions, context limits, configuration names) — the shape is stable; the numbers are operator configuration.*

*Revised 29 September 2026 against the checkout at `8109428`, after the compaction-boundary audit, the guard-estate census, and the build packets BD-2, BD-3, v3.1 Phase 1a and 1b, and FC-0. Where a claim in an earlier revision was found stronger than the code, the correction is stated in place and the earlier wording is not preserved. Two claims in the 28 September revision were contradicted by later measurement and are corrected here rather than left: the cascade's escalation behaviour (§2) and the status of work-unit attribution (§7, §10.4).*

## 1. The shape

NEXUS is a single-process Python service: a FastAPI application over an async turn loop, with SQLite storage on local disk (or Postgres, for the hosted profile) and a model behind one provider abstraction: a local runtime (Ollama or LM Studio), an API (OpenAI-compatible or Anthropic), or the stub. There is no distributed component. The core path depends on no external service when the model and the store are local; with an API model or a Postgres store, the turn depends on that service.

Six layers, each with a responsibility and a prohibition:

| Layer | Package | Responsible for | May not |
|---|---|---|---|
| **Providers** | `backend/providers` | Talking to the model runtime: streaming chat, embeddings, installed-model listing. Maps *canonical roles* to backend-specific model names. | Appear in routing logic by model name. Routing speaks capabilities; names live only in the provider map (a static guard enforces this). |
| **Router** | `backend/router` | Choosing a model per turn by *capability*, from a registry of model profiles (capabilities, footprint, throughput). Handles operator overrides and model-pull proposals. | Reference a model name in a branch; mutate shared registry state (each app instance gets its own copy). |
| **Loop** | `backend/loop` | The turn itself: context assembly, streaming, extraction, per-turn learning, compaction of the prompt, an isolation surface for tool-running workers. | Mutate conversation state in place — state is a frozen dataclass replaced atomically at the end of the turn, never edited. |
| **Cortex** | `backend/cortex` | The in-memory association machinery: spreading activation over a session graph, Hebbian weight movement, a pre-retrieval citation forecast, contradiction detection, triple extraction from answers, and a curiosity pass — gap detection over graph topology, ranking the nodes the graph leans on most heavily while weighting them least, and phrasing each as a question. | Write to the belief store except through the one admission chokepoint (below). Curiosity in particular writes nothing: it reads the live graph and emits, and its output is not persisted anywhere. |
| **Memory** | `backend/memory` | Durable memory: the session graph's persistence, consolidation into the belief store, answer-lineage records, a hash-chained archive with periodic snapshots, and the background scheduler. | The background process may not write the archive from the request path — the archive has exactly one writer, the scheduler. |
| **KB** | `backend/kb` | The belief store: a tiered triple store with an admission gate, retrieval (lexical, semantic, and an association-trail channel), governed weight recalibration, archival with a durable act ledger, deduplication. | Delete anything, ever. Rows are archived (standing removed, record kept) — no code path deletes a belief. |

Two small supporting packages: `backend/vector` (embedding calls and a vector store that is currently structurally dark — see §7) and `backend/eval` (per-turn scoring and an append-only calibration ledger). The repository also ships two single-file HTML frontends (a main console and a memory view) with no build step; they consume the same HTTP and event surface an integration would, and are clients of the system rather than part of its core. A cloud deployment is described in §10: its container image, compose profiles, Postgres store and identity from a proxy are built (`docs/DEPLOY.md`); its replicas and shared state are design, and §10 is the one place this document describes what does not yet exist.

**The design's central separation, which everything above serves:** every belief has two kinds of value. The **record layer** — what was claimed, by which source, when, and every governance act about it — is lossless and append-only. The **prominence layer** — what a belief is currently worth in ranking — is lossy by design: it decays with disuse, is discounted by evidence class, and moves only through recorded, policy-bounded events. Guards exist specifically to keep these from leaking into each other, in both directions.

## 2. The request path

One endpoint carries conversation: a chat request streams Server-Sent Events until a terminal `done` frame. The stages, in execution order, with what each may touch:

1. **Queued alert drain.** Maintenance findings produced by the background process (duplicate candidates, drift, pressure alerts) surface as events at the start of the next turn — the background process has no live channel of its own by design.
2. **Citation forecast** *(before any retrieval)*. A read-only spread over the session graph, seeded from the query's terms alone, commits a ranked prediction of which beliefs the answer will cite — persisted to the calibration ledger before retrieval runs, so the prediction cannot be fitted to what retrieval finds. It reads the graph without mutating it.
3. **Retrieval and context assembly.** Two proposal steps run against the incoming message first: statements the user made that could become beliefs are *offered* for confirmation (never stored uninvited), and a web-search step may *propose* a search — executing one requires a prior, single-use, explicitly-confirmed consent, and its results are injected as clearly-sourced context, never as beliefs. Then the belief store is queried through up to three channels (lexical match; optional semantic similarity; optional association trails), unioned into one candidate pool and ranked by a single ordering — prominence-tier first. Substrate-generated association rows are capped to a bounded share of the context. Retrieved matter is folded into the session graph and spreading activation runs from it; the top of the activation map is rendered into the prompt alongside the retrieved claims. A stable system prefix is never modified by any stage (guarded — see §5).
4. **Routing.** The kernel selects a capability; capability resolves to a role; the role resolves to a backend model name in the provider map. An operator override (by role or raw name) wins; extraction is immune to override. If routing lands on a model other than the one loaded, a swap is announced on the stream before it happens, with the prior and next model named.
5. **Compaction**, when it fires. A four-tier cascade — snip, micro, collapse, auto — runs under an integrity check that reports WARN or PASS per rule on every fire and emits the report on the stream. Nothing halts and no state is marked: the FAIL tier that the constitution once described was found unreachable by every rule and was retired with a recorded decision. The check reads the graph and the session claims, never message text; on its inputs it is live at tier 2 and cannot fire at tiers 1, 3 or 4. **How it decides, settled by the cascade establish (3 October, rig only):** at entry and after each of tiers 1–3, the cascade compares the live token estimate against the next tier's threshold (5,734 / 6,553 / 7,208 / 7,782), stops if it is below, and otherwise fires that tier and checks again. Tiers 1–3 edit session memory, the graph context and the graph, none of which the estimate counts, **so the tier reached is simply the highest threshold the entry estimate has crossed.** The two earlier rig runs that appeared to disagree ("escalates every time" against "usually stops early") were both right about their own starting points: one began above the tier-4 threshold, and the other grew through the lower ones turn by turn. **Tiers 1–3 also do not reduce the next turn's context:** on the rig, 11 of 11 next-turn estimates and their content were identical with those tiers disabled, because the turn's later stage rebuilds session memory and replaces the graph context wholesale, so their edits do not survive the turn. **On the rig, then, only tier 4 changes what the model sees.** It drops whole messages and replaces them with a code-written count stub inside a runtime-delimited block. Compaction runs second in the turn, after retrieval and before the model call. These are rig results. **The instance cannot confirm them yet, because compaction reports live only in an in-memory ring; a durable capture is the queued successor.**
6. **Streaming.** Tokens are held until the turn's record is written and then released in order (W6, `NEXUS_ANSWER_RELEASE=after_record`, the default); under `live` they stream to the client as they arrive. A turn whose record cannot be written ends with `record_failed`: under the default no frame of its answer is released; under `live` its tokens have already gone.
7. **Post-answer accounting** (the client continues to receive events): triple extraction from the answer via a second, smaller model call — every candidate passes the admission gate, and refusals are counted and declared in the turn's summary rather than dropped — declared, not recorded: a candidate the gate refuses was never a valid claim and leaves no ledger row, whereas a refused well-formed request for a governed act is both declared and recorded (see §3); contradiction detection (retained and surfaced, never resolved — see §3); the **lineage record** — which beliefs were injected, at what weight, and which the answer actually *cited* — decided by citation extraction: a whole-token match of the claim's subject and object against the answer text, lexical rather than semantic, which measurement puts at roughly a fifth of items under-reported (see §7) — hashed and stored; calibration accrual and forecast scoring against the now-known citations; the **citation capture**, when enabled — one row carrying the answer text, the injected surfaces as the model saw them with belief id and cited flag, and the lineage id, written only if a lineage record exists to join to; it reads what the stage has already produced and changes no flag, weight or decision; the **curiosity pass** (since AX.1 on the idle cycle, not the turn: `NEXUS_CURIOSITY_PLACEMENT=idle`, its questions reaching the next turn as `curiosity_surfaced` frames) — a read of the live session graph (its degree structure and per-node evidential weight, nothing else) that ranks the load-bearing nodes the system understands least and emits each as a `curiosity_surfaced` event; it touches no store, mutates nothing, and its questions exist only as frames on the stream; bounded Hebbian movement over the turn's most co-active nodes; atomic state replacement; reinforcement — only *cited* beliefs get their decay clock reset, retrieval alone confers nothing.
8. **`done`**, carrying the turn's declared accounting: what was injected, cited, reinforced, suppressed; what extraction stored, decomposed and refused, with reasons; the forecast's score beside its control. After the stream closes, the session graph is persisted under a lock shared with the background process.

**Frame order on the wire is not stage order.** The stages above are execution order. On the stream, the `turn_start` frame is emitted after routing and compaction, immediately before the injection accounting for stage 3 — so queued alerts, routing frames and any compaction report arrive before it, and the stage-3 accounting (`triples_injected`, `graph_activating`) arrives after the stage-4 and stage-5 frames. A reader mapping frames to this numbering should map by frame name, not by arrival position.

**Where an integration sits.** A consuming platform talks to the HTTP surface: the chat stream, the read surfaces (stats, health, lineage, provenance, governance), and the confirm-gated write endpoints. Every state-changing operation of consequence — seeding, deduplication, assertion, outcome recording, policy installation, index backfill — is behind an explicit confirm contract: the request must carry an explicit confirmation flag, and a bare proposal returns what *would* happen. An integration therefore has a natural two-step shape: the system proposes (via events or pending-listing endpoints), the platform confirms. Requests may carry a scope label and an actor identity on governance operations; both are recorded, never inferred from content.

## 3. Storage

| Store | Medium | Holds | Authoritative or derived |
|---|---|---|---|
| **Belief store** | SQLite (or Postgres) | Triples: subject/relation/object, source, prominence tier, weights, archival status; plus governance tables (outcome events, recalibration events, policy versions, archival acts) and the association-trail tables. | **Authoritative** for claims and governance. |
| **Session graph** | In-memory, persisted to the same SQLite file each turn and each maintenance cycle | Association edges with firing/recurrence counters and timestamps. | **Authoritative** for association state; survives restarts via its persistence table. |
| **Lineage records** | SQLite | Per-turn evidence records: injected beliefs with weight-at-injection frozen, per-belief cited flags (lexical detection; positives more reliable than negatives, see §7), contradictions, model identity, prompt-prefix hash, the dynamic block recorded re-derivably, a hash of the conversation history, response hash; and, when the caller supplies them, the work unit, the accountable identity, the asserted decision boundary and who asserted it — the whole record hashed, the attribution fields only when stated, so a record that predates them recomputes byte-for-byte as before. | **Authoritative** for "what did this answer rest on". |
| **Work units** | SQLite | One row per unit of work a caller names: type, accountable identity, the actor fields of whoever first mentioned it, open and close timestamps with who asserted the close, a session id, and an attribution status. Created on first mention; never inferred. A caller that names nothing gets a session pseudo-unit, reported separately as unattributed. | **Authoritative** for attribution. |
| **Claim-to-unit junction** | SQLite, append-only | Which claims were *admitted* during which unit, with the turn and the lineage id of the answer that admitted them. A claim re-asserted in a second unit gains a second row; its stored row is untouched. Closing a unit touches neither. | **Authoritative** for admission. *Use* is derived from lineage, deliberately not stored here — writing it would import the citation flag's measured under-report into attribution. |
| **Archive chain** | Separate SQLite + JSON snapshot files | Hash-linked blocks: periodic structural snapshots of the session graph, and seals over lineage and governance record hashes. | **Derived** (seals and snapshots of the above), but the tamper-evidence anchor. |
| **Calibration ledger** | Append-only JSONL | Stated confidences with later-arriving outcomes; forecast commitments and resolutions. | Accrual only; latest-row-wins on resolution; nothing rewrites a line. Not hashed or sealed; append-only by code discipline. |
| **Citation capture** | Append-only JSONL, off by default | Per captured turn: the answer text, the injected surfaces byte-for-byte as rendered into the prompt with belief id and cited flag, and the lineage id. Exists to be labelled. | **Derived, not record.** Not sealed; verifiable against the sealed record because the captured answer must hash to the lineage record's response hash — a sentinel pins this. Holds conversational text in plaintext. |

**The write chokepoint.** Every path that admits a belief — extraction, seeding, human assertion, consolidation, procedural promotion — goes through a single `add()` on the store, which runs an admission gate (class-aware rules over term shape, markup, error text, stringified nulls, and more) and upserts monotonically: a re-assertion can raise a stored weight, never lower it. Enforcement is structural, not conventional: a static test enumerates every ingest route and fails if one bypasses the chokepoint, and another proves the stored weight column has exactly one writer.

**Contradiction is retained, never resolved.** Two conflicting claims coexist, both retrievable, the conflict surfaced to the client and recorded in lineage. Removing one side is a human act (archival or a recorded outcome), never automatic. This is a deliberate property for evidence-record use: the losing side of a disagreement, and who adjudicated it, stays answerable.

**Prominence's stored inputs move only as recorded events; prominence itself also moves on the clock.** Effective weight is computed at read time as `clamp(max(0, weight − rate(class) × days since last_fired) × arrival_scale(class) + recalibration sum)` (AS-2, October 2026). It reads neither `fire_count` nor `tier`. Of its inputs, the stored weight is a monotone maximum with no dated history, `last_fired` has one writer in the record (`fire`, as a lower bound) and one outside it (re-assertion through `add()`), and the class constants are code-versioned and unrecorded; so the value the model saw on a past date cannot be rebuilt from the record, while `fire_count` on a past date can be, exactly, as the count of cited injections under live learning. Under a freeze nothing refreshes `last_fired`, so counters are preserved and standing drains. Recalibrations are policy-bounded (an installed, versioned envelope caps step size and cumulative movement per belief), actor-stamped, and sealed. Archival likewise: status lives on the row, but every archive/unarchive **act** is its own append-only ledger event with actor and reason, sealed with the governance records — reversing an archival does not erase the record that it happened.

**Derived stores bind to the record by hash.** A store that sits outside the seal can still be vouched for: the citation capture is accepted only if its answer text hashes to the sealed lineage record's response hash, so a tampered or mismatched capture is detectable without the capture itself being sealed. The calibration ledger is the other unsealed store and does not yet have this bind; its forecast rows join lineage by entry id, and hashing them to the record they predicted would give it the same property at no sealing cost.

**Recorded re-derivably, or hashed only.** Two different claims, and the record makes both. The dynamic portion of each request — the store-derived context lines and the runtime-written blocks — is recorded such that every line can be re-derived from the record and the store and compared; a static guard proves the derivation. The conversation history is hashed into the record but not retained beyond an in-memory checkpoint, so a change to it is detectable while the original is not recoverable. A reader should not take the second for the first.

**The governance reporting surface.** Two read-only surfaces sit over the governance record, both deliberately outside the alert stream (alerts render to whoever is chatting; these are operator surfaces, token-gated):

- **The budget report** aggregates governed movement against the policy that permitted it: per belief against its cumulative cap, per actor split by role (a person and a source system are never summed into one row), store-wide with refusals and their rules — anchored to the policy version each event itself cites, so "consumed under version N" is a fact against a signed policy rather than an inferred normal. Steady pressure at the limits is visible even where every individual step was legal. The payload declares its own limits on its surface: the cumulative cap is per-belief only (no per-actor or store-wide budget exists in the policy object, so spreading small movements across many beliefs consumes nothing any cap watches — the report can show that concentration; the policy cannot currently refuse it); it sees governed movement only; and its coverage begins where its records do.
- **Verification endpoints** recompute every governance record's hash and check sealed ones against their chain blocks, reporting failures by layer (content edit vs seal mismatch vs chain break) rather than collapsing to a boolean.

**The honest boundary, stated as the design's current answer to the contamination question:** contamination is attributable and findable afterwards at the governance layer; at the belief layer it is attributable only to an evidence class (beliefs carry a source class, not an identity); and nothing at either layer would notice it *accumulating*. Slow accumulation through the governed door shows up in the budget report's aggregates; accumulation through ordinary claim entry does not, because no aggregate watches it. This is a known property, recorded on the report's own surface, not a discovered gap.

## 4. The background process

A single in-process scheduler (KAIROS) wakes on a short poll and runs only when the session is idle. Its cycle, in order: consolidation of qualifying association edges into the belief store (through the same admission gate as everything else, refusals counted per belief); tier rebalancing (an idempotent projection of every belief onto the tier its computed prominence implies); graph decay and demotion (demotion reduces visibility, never deletes); procedural pattern promotion; a duplicate scan that only ever *proposes* (archival requires operator confirmation); semantic-index backfill in bounded batches; session-graph persistence; and sealing — a periodic structural snapshot block, plus a more frequent governance seal that covers any unsealed lineage, recalibration and archival records.

What it may not do during a request: it checks a session-active flag — set by the turn loop before a stream opens and cleared in its `finally`, so an aborted turn still releases it — and additionally takes a shared lock around graph persistence, so a turn's graph write and a cycle's cannot interleave. It is the **only writer of the archive chain** — the request path writes the operational stores and leaves sealing to the cycle. It has no direct client channel; anything it wants a human to see is queued and drained at the next turn (or read from status endpoints).

**The drift check.** At each snapshot, the cycle compares the new structural fingerprint against the previous snapshot's and escalates through warn/alert severities, surfacing an alert (with a recommended action it only ever *recommends* — nothing acts on it automatically). Two current-state properties an assessor should know: its subject is **session-graph topology, not beliefs** — the belief store never enters the fingerprint, so this is not a contamination or content-drift detector; and the distance measure is **dominated by raw node/edge counts**, so ordinary growth between snapshots can cross the warn line on its own. Both are recorded properties of the mechanism as built.

Failure discipline: a refused belief inside a cycle is counted and skipped, never allowed to abort the cycle; an aborted cycle reports its fields as unknown rather than zero, so a default can't impersonate a measurement.

## 5. What is enforced structurally

The test suite (about 4,000 tests across 215 files) contains, beyond behavioural tests, a set of **static guards** that parse the source (AST, never text search) and fail the build when a structural property breaks. The significant ones, and what each proves:

**Boundary and chokepoint guards.**
- *Single ingest chokepoint:* every route that stores a belief is enumerated and shown to pass through `add()`; a new route that doesn't fails.
- *Single writer for stored weight:* the belief's stored weight column has exactly one writing statement; anything else that writes it fails.
- *Reserved-channel grant:* one calibration mechanism is writable from exactly one module; the guard fails both on a second writer and on the grant going unused.
- *Import purity:* importing the service module constructs nothing — no store, no file, no connection; applications are built only through an explicit factory. Enforced by test after a real incident in which a bare import migrated a live database.

**Gate-bypass prevention** — the security-relevant class, and it exists because every gate has a raw primitive underneath it that performs no checks. The Law-3 confirm endpoints are the *front* doors; these guards are what stop a future code path using the back ones:
- *Caller pins:* the raw recalibration insert (which performs no policy checks — all policy lives in its one gated caller), the archival primitives (mass invalidation-in-effect if reachable ungated), and the store-to-graph ingestion call (the one path that copies a stored weight onto a live edge) are each pinned to **exactly their current callers, in both directions** — a new caller fails the build until deliberately acknowledged, and a vanished caller fails so the pin cannot rot into reassurance. Each pin ships with a non-vacuity companion proving the detector sees the exact shape of a rogue caller.
- *The read-pin, specifically:* most guard systems watch writes; one of these pins exists because a leak was found in the *read* direction — the record layer's monotone value flowing back into the prominence layer through an innocent-looking read. The pin holds the call sites of the one store-to-graph ingestion function to exactly one, with the substrate/claim distinction enforced at that site. Two other stored-value copies remain outside it and are recorded as the next scope: the upsert's refresh of a re-promoted row's last-fired timestamp, and start-up restoration of persisted edge weights.
- The distinction from the behavioural tests matters here: these fail at build time, on the parse, before any code runs — a bypass cannot exist in a passing build, rather than being caught when exercised.

**Contract reconciliation.**
- *The event contract is reconciled three ways, by name:* the declared event list, the events the code can actually emit (by reachability analysis, not by searching for emit calls), and the events the frontends bind are compared; known gaps are pinned as explicit exceptions that fail when they grow *or* shrink, so closing a gap is a deliberate act. What is reconciled is the set of event *names*. Payload shape is not: the declared list carries an indicative key set per event, and for at least two events (`curiosity_surfaced`, `done`) the emitted payload has more keys than the declaration. An integration should take field names from the emitting code or from `docs/INTEGRATION_REFERENCE.md`, not from the declared list.
- *Auth coverage is derived, not remembered:* the set of state-changing routes is read from the running router and compared against an acknowledged list; every writer is tested for missing-token, wrong-token and correct-token behaviour; read routes must be either explicitly classified as deliberately open (with a recorded reason) or actually gated — an unclassified route fails.
- *Configuration is probed, not trusted:* every documented setting must have a test that sets it in a real configuration file and observes the consumer honouring it, in a fresh interpreter; documented settings with no reader are pinned as such; every documented rollback position must be exercised by at least one test.

**Layer-separation guards.**
- *Ranking ignores similarity:* retrieval's sort key is pinned so semantic similarity contributes candidates but never order — a paraphrase cannot outrank an assertion *by being worded like the question*. The pin is denylist-shaped: it requires the prominence term and forbids the similarity names, so a new sort term of another kind would pass it. And provenance is a discount within standing, not a strict first key: rank is tier, then class-scaled prominence, and tier is itself a band of prominence, so an extraction-class row with high prominence can sit above a human-asserted row of lower prominence in the same band. "Ordered by provenance" overstates; "ordered by standing, in which provenance is a discount and similarity is absent" is what the code does.
- *Record/prominence separation:* the forecast must be persisted before retrieval runs (proven by parse-order over the turn function *and* at runtime); the store's monotone weight may not be copied back onto live association edges for substrate-generated rows; the Hebbian pairing input is pinned to the turn's activation map so a popularity signal cannot be substituted.
- *Prompt stability:* the system prefix is asserted bit-identical across compaction and across model override, at assembly and in the cascade's own rule. The cascade's rule was found in September to compare a value with itself and was replaced; its companion now asserts the WARN it produces on an altered prefix.

**Measurement honesty guards** — a distinctive class: a measurement's fixture must be calibrated against evidence the measurement did not produce; measurement scripts must refuse degraded inputs (an unavailable embedder aborts with a named exit code rather than producing a ranking from noise) — the embedding-dependent scripts and the separation scorer carry this; the older scripts predate it; growth-*order* assertions run across multiple sizes rather than fixed thresholds, because a fixed threshold passes on a fixture too small to expose the problem.

**Population discipline.** Test enumerators draw file populations from version control, never the filesystem, so an untracked scratch file cannot change what a guard covers; guards that inspect source must import their subject (parse-acceptance alone has been shown insufficient); platform-shape guards forbid patterns that have broken the second platform before (path-separator handling, hand-built subprocess environments, unpinned encodings). Two further guards in this class are what keep tests off real data: persistent writers built as classes are *derived* from the data-path constants and wrapped automatically; writers built as functions are outside the derivation and are ratcheted through an acknowledged list instead, so a new function-writer is caught by the unconsumed-constant sweep rather than derived — a weaker net, and the recorded next step is to extend the derivation; module-scope construction is forbidden; and no test may construct a networked provider implicitly. Two more are pattern guards over the whole backend rather than call-site pins: every store admission inside a loop must catch a refusal per belief, count it and continue — so a cycle cannot abort on one bad row — and the terminal `done` frame is pinned as the final frame of every stream. The `triples` schema is pinned two ways: the store's columns against the DDL, and the DDL against a test-side answered-for set, both as set equalities, so a column arrives on that table only by a recorded decision — this replaced a guard that pinned one literal name and passed every other.

One runtime check sits beside the static estate and is named here with what it does and does not do: prompt **compaction runs under an integrity check** on every firing that reports, per rule, whether a concept vanished, whether minority claims were lost disproportionately, whether edge loss was disproportionate, and whether the prefix is intact. It reports WARN or PASS; it never halts. **Each report carries the vanished-concept rule's full set structurally — every removed id, sorted, and its count — beside the five-name string that is now a display slice and no longer the only record.** Before that fix the rule computed the set and wrote only the truncated string, so a reader could not tell five removals from fifty, and every fire before it is under-recorded on the stream and unrecoverable. Three rules that compared node epistemic states across the boundary were retired when the state was found to be written once and never updated; a rule about source-attribution loss that the constitution described was found never to have existed in code and is now recorded as an unbuilt aspiration. The check is a runtime property because its subject only exists at runtime; it is a report, not a guard, and the document no longer calls it one.

The honest limit of all this, in two parts. First, these guards prove *structure* — who may call what, what is declared, what is separated. They do not prove retrieval quality or learning quality; those are measured by scripts against real stores, and several of the system's own headline numbers have been corrected by exactly that process. Second, a census of the estate itself (27 September; the script is committed) counted 135 structural guards across 61 modules, of which 27 have a companion test that plants a violation and proves the detector fires; of those 27, 12 plant only the case the guard names, and one asserts a flag rather than a consequence. The remaining 108 are claims with no witness. Two rules became binding constitution on that finding: every guard has a witness, and the witness plants what the guard does not name. The 108 are recorded, not fixed; a reader should weight any guard named in this section by whether it has a companion, and the census lists which do.

## 6. Integration surface

A consuming platform:

- **Calls:** the streaming chat endpoint (message, optional scope label, optional attachments, and the optional attribution fields below); read surfaces for stats, health, model status, lineage records and per-belief provenance, governance verification, and the budget/coverage reports; pending-listing endpoints for everything awaiting confirmation.
- **Must supply:** a bearer token on every state-changing call and on evidence reads; explicit confirmation flags on the Law-3 gates (nothing destructive or externally visible happens on a bare request); actor identity on governance operations if attribution beyond the local default is wanted; its own handling for the event stream, including the declared alert types and the curiosity frames — the latter have no other outlet: they are neither persisted nor summarised in the terminal frame, so a client that does not bind them has discarded them.
- **Gets back:** the token stream and a terminal summary that *declares* the turn's accounting (injected/cited/reinforced/suppressed, extraction admissions and refusals with reasons, forecast score beside its control); stable identifiers (lineage ids, belief ids, event ids) that join the evidence, calibration and governance records to each other; and verification endpoints that recompute every sealed record against the chain on demand.
- **Can always see the configuration and coverage in force:** the stats surface declares, per subsystem, what is actually loaded and where each ledger's records begin (the vocabulary and opposition set in effect with their sources, semantic-index coverage, scope and archival-ledger coverage notes, suppression counters); the health surface declares degradations as they happen, including a monotone did-it-ever-degrade counter distinct from is-it-degraded-now. The design treats "silently running on defaults" as a defect class, so an integration can verify its configuration took effect by reading, not by trusting.

**Attribution, one channel.** The chat endpoint takes a work unit and its type, an accountable identity, a decision boundary, and three actor fields — **all as body fields, and only as body fields.** The `X-Nexus-*` headers an earlier draft specified are not read and a static guard over the route forbids reading any header there, with a behavioural test that sends them beside the body and asserts they name nothing. Two channels for one value was the only way a request could contradict itself about which unit it was in, and a contradiction the system must adjudicate becomes a guess written into a sealed record; one channel makes it unrepresentable rather than resolved. A gateway that needs headers gets a deployment setting that selects the source, later and in one place, not a second live channel. The same field is accepted on the assertion and seed routes, so a caller working inside a unit is attributed there too. Everything supplied is recorded literally and sealed; nothing is inferred, and **a turn inherits nothing from the turn before it** — a test proves that, and it is what keeps the lifecycle from returning.

The endpoint-by-endpoint contract — request and response shapes, the confirm-gate pattern, error conventions, pitfalls — is maintained separately in **`docs/INTEGRATION_REFERENCE.md`** (and a self-contained HTML rendering beside it), derived from the router at a named commit. Seven test files read parts of it and fail when those parts drift; the rest fails nothing when a route drifts from it, and its own header says to verify against the live OpenAPI at `/docs` when the router is newer than the reference. This document deliberately does not duplicate it. Two facts from it that a partner should not discover late: `GET /events/recent` is an open route under the localhost-bind posture and replays the last 200 loop events *including answer text*, so a deployment reachable beyond localhost must gate it; and no route lists archival acts — the ledger's rows are counted and integrity-checked over HTTP but not returned, so "who archived belief N" is a gap today, not a route a reader has missed.

Plainly, as of this document's commit:

Two of the numbers: the pairing step that compared every edge against every other ran 987,319,778 operations per turn and took 6 minutes 52 seconds, during which the turn's record could not seal; bounded to the twenty most-activated nodes it runs 190 operations in 70 milliseconds. On the operating store, 21,929 of 22,277 rows were substrate exhaust; a recorded archive pass set aside 21,915 of them, retrievable dropped from 22,277 to 362 with the record intact, and 14 were exempted because sealed answers rest on them. The fourth loop — redefining what counts as a co-activation episode — is designed and pending. Until it lands, consolidation is muted by configuration on the operating store and the legacy association rows are being archived under the recorded-act ledger. **Learning on the reference instance is frozen since 2026-10-01, until the recurrence fix lands.** From 5 September it was only muted: a recurrence threshold of 999 stopped promotion into the store and nothing else, as measured on 30 September. Per-turn association updates, reinforcement, tier rebalancing, procedural promotion and trails all continued. A declared switch replaced it: with `NEXUS_LEARNING=frozen`, five store methods refuse every automatic, unconfirmed learning write. Retrieval, extraction, the lineage record and confirmed acts are unaffected, and the state is declared on every turn's `done` frame and on `/cortex/stats`. In the first minutes of the freeze, the consolidation gate reported 44,547 edges that would have been promoted at the shipped threshold, which is the scale of the counter defect the recurrence fix addresses. Every learning claim in this document is subject to this line. Downstream defences (a share cap in retrieval, exclusions in the semantic index) remain in place and are documented as symptom containment, not cure.
- **Citation extraction is lexical, and it under-reports by about a fifth.** Which claims an answer used is detected by a whole-token match of the claim's subject and object against the answer text. It has no notion of meaning, and it fails in both directions: a claim the answer restated briefly, or in other words, reads as not cited; shared terms with a different assertion read as cited; and near-duplicate claims against one sentence present attribution ambiguity that no per-item test resolves. This is now measured rather than suspected. On a class-stratified sample of twenty disagreements, judged blind against a threshold fixed before any number existed, an entailment model was right nine times in ten where the lexical test said *not cited*, and the lexical test was right six times in ten where it said *cited*. Extrapolated across the store that is roughly 190 missed citations, about 22% of items; the positive flags are more reliable than the negatives. Three mechanisms inherit the judgement — reinforcement, the archival exemption and the forecast's scoring — and a reader who takes the flag as reliable will take those three as more reliable than they are. The entailment model was tested as a replacement under the pre-registered protocol and did not clear the bar: 13 of 20 against a threshold of 14. The incumbent stays, by the tie rule stated before the run. Where human labels are recorded is not yet decided: a label is a judgement that an answer rested on a belief, which is an outcome event in this document's vocabulary, and whether it enters the sealed record or a side file is open.
- **Attribution is assessed separately from generation.** A model's own inline citations have been shown, in a mechanistic study of one instruction-tuned model, to rely on entity co-reference matching between document and question rather than semantic integration during answer construction (arXiv:2606.28358). Self-reported citation would therefore conceal the heuristic rather than replace it, which is why citation extraction runs over the finished answer and the injected set, and why its accuracy is measured against human labels rather than against the model's account of itself.

The rule that a default may not impersonate a measurement is enforced at the three sites in §8; this list is its known remaining scope.

Two prerequisites were named and are queued: predicate identity (nine spellings of the typing relation are live) and a governed way to declare a cell not-applicable. Whether a customer's store with an asset register or a reference vocabulary could support the design is a different question from whether this one does. The scaffolding-pollution finding stands and is fixed upstream for new rows only. Curiosity's read-only relation to the graph is still a property of the code as written, not a guard.
- **The conversation-history path is the weakest point on the request path, and it is measured.** An audit against the September 2026 compaction-report findings placed the runtime at level 2 of 5 on one property: prior assistant answers are carried into the next prompt verbatim, unbounded and labelled only by role — the path those reports' self-authored summaries travelled. The cut unit was corrected to a sentence boundary and the cap set in characters from the 480 measured answer lengths (`HISTORY_ANSWER_CAP_CHARS = 1800`, pooled p95 1,772), provisional until a week of real lengths exists. `NEXUS_HISTORY_WRAP=off` restores the pre-A path byte for byte. The claim path — model-chosen fragments reaching the next prompt only through the gate, under eight tokens, inside a runtime-written block — is at level 4. Nothing here reaches a successor that conceals without being told; that is a property of training, not of this runtime.
- **The model's reasoning is separated from its answer at the provider boundary** (C-38, `b2dab78`, 18 October 2026). Every provider returns answer, reasoning and raw; every consumer of the model's text (history, extraction, the citation detector, the console stream, the capture, the evaluator) receives the answer only, and the single reader of the reasoning is the record, which keeps its length and hash and never its text. NEXUS asks the daemon for nothing and reads the separate field when it is sent (asking can return HTTP 400 on a manifest without the capability); a per-model tag parser covers inline reasoning. An answer that is empty because the reply was cut off inside its reasoning is a declared state, never a fallback to extracting from the reasoning. On the operating instance (Ollama 0.18.0) the reasoning runs two to three times the answer's length and had never reached NEXUS before this change; 0 of 480 measured production answers carried it inline. The extraction window (4,000 characters, head first) is declared on every turn and unchanged.
- **The session graph's per-node epistemic label is false and is being retired.** Every node carries `known` / `inferred` / `speculative` / `contradicted`; the code assigns `known` to everything retrieval touches, `partial` to query terms and rehydrated nodes, and never produces the other values — so the label means "created by retrieval in this process" and nothing about evidence. It is rendered to the model only under the documented legacy render (`NEXUS_PROMPT_RENDER=legacy`), where it tags extraction-derived concepts as known; that rollback is pinned byte-for-byte, so the pin faithfully preserves the falsehood. The decision is to retire the label rather than make it live, because its honest originals — source class, contradiction record, outcome event — already exist in the store; the retirement and the legacy-render decision are queued, and the constraint on them is recorded: a false signal is not removed without the true one taking its place where it stood. The claim the retired invariants protected, "compaction cannot upgrade a belief", is held open in the register on its own line until its new home lands or it is retired deliberately.

A regret-shaped definition — a concept removed by compaction being activated again within a pre-registered window, against the base rate of any concept activating — is defined and queued. `retention_rate` is not the metric: compaction is supposed to drop things. **The capture that would feed it was drafted and withdrawn before a line was written**, at its own establish: the removal rule wrote its set only into a truncated display string, so the capture's primary field existed nowhere structural. That instrument is now fixed (§5). **Two findings from the same establish decide what a successor can measure.** `graph_context` lives one turn — it is replaced wholesale by each turn's hits — so *removed by compaction* and *not re-retrieved this turn* are the same event on that state, and a regret measure has to be defined against that rather than against a retained context which does not exist. And micro removes nothing in ordinary use: on a 40-turn rig it fired fourteen times and carried **zero** concept removals, because a row in the graph context was ingested the turn before and therefore has an edge. **The tier that does the work — tier 4, which drops whole messages — is the one nothing characterises.**
- **Retrieval rank is standing with a provenance discount, not provenance first.** §5 states it; it is repeated here because two earlier revisions of this document and one of its companions said "ordered by provenance". The record layer is contained (a re-assertion by extraction of a human claim is a different row and cannot raise the human row); the read side that builds the prompt is not class-first.

The instrumentation to score them (forecast-vs-null per turn, calibration resolution) is in place and accruing; the volumes are not yet large enough to support a number, and the project treats early numbers as noise rather than signal.

## 8. What is distinctive

For an assessor deciding where to look first. Five mechanisms are unusual — an inference about the field, marked as one; that each exists as described is checkable from the tests named. Each is given as: what it does and why it matters, what it was built after, what proves it, and its current edge.

**1. A guard on the read direction between the record layer and the prominence layer.** Every belief has a monotone stored weight — the admission chokepoint's maximum across every promotion, a record — and a live association weight that decays and moves. Guards elsewhere in the estate stop writes crossing that boundary. This one stops a *read* crossing it: the substrate/claim distinction is enforced at the single site where a stored weight can reach a live edge, and that site's call set is pinned to exactly one in both directions. It was built after a retrieved substrate row copied its stored weight onto its edge and, in the commit's words, undid Hebbian weakening and days of scheduled decay "in a single assignment: I-8 violated in the one direction nothing guarded"; the operator saw four substrate rows at full prominence ranked above every real claim. The sentinel test runs a real decay pass and proves the edge stays decayed through a retrieval. The pin covers this path; two remaining stored-value copies — the upsert's last-fired refresh and start-up restoration of edge weights — are recorded as the next scope.

**2. A preregistered prediction on every turn.** Before retrieval runs, a read-only spread from the query's terms commits a ranked forecast of which beliefs the answer will cite, and the row is on disk before retrieval starts. Each turn is then scored against a null built from the same turn — the injected set ranked by prominence at injection — so the forecast has to beat the obvious predictor, not zero. The system makes a falsifiable claim about its own retrieval on every request, and cannot fit the claim to what retrieval finds. Three guards prove it: a parse-order test asserts the forecast call precedes both the first context-assembly call and the first assignment of retrieval hits; a runtime witness reads the ledger at the instant retrieval is invoked and requires the row present; a module guard forbids the forecast module from reaching any retrieval function. The commitment is ordered, not sealed — the ledger is append-only by code discipline, not hashed — and the per-turn score is declared on `done` while per-belief outcomes are what persist. Scores accrue; the aggregate surface waits for volume.

**3. Pins that fail in both directions and prove they can fail.** The contract test's pinned exception set is asserted by set equality: a new gap fails the build, and so does a closed one. The comment on the pin is the design statement: "the pin is the finding … closing it should be a deliberate, recorded act rather than a silent drift in the direction we happen to like." The same shape holds for the auth writer set, the three caller pins on the dangerous primitives, the configuration probes, and the reserved calibration grant, which fails on a writer outside it and on the grant going unused. Every caller pin and the read pin ships with a companion that plants a rogue caller of the exact shape and proves the detector sees it — a guard that cannot fail is not a guard. Two guards are one-sided on purpose: the documented-but-unread settings set outlives its documentation by design, and the retrieval sort-key pin has no shrink direction. The companions described here are the ones the census found: 27 of 135 structural guards have one, and the discipline this paragraph describes is now binding for the rest rather than assumed of them (§5).

**4. Measurements that cannot measure themselves.** No test may move the shipped similarity threshold; a guard parses the test file's own source and fails on any override. The audit tool for the semantic fixture may not import the embedding machinery it audits. Growth is asserted as order across doubling sizes, never as a fixed bound. Embedding-dependent scripts refuse to run without a live embedder and exit by name: a hash fallback carries no semantic signal, and a number computed from it would not be a measurement. Each guard was built after the failure it now prevents. The threshold pin: a default shipped above both measured signals, and no test caught it because every test set its own. The growth-order pin: a fixed bound passed on a fixture too small to expose a quadratic, which is how a 67-millisecond sandbox measurement and a 412-second production reality coexisted — the pairing step ran 987,319,778 operations per turn; bounded to the top twenty activated nodes it runs 190, and the guard now asserts the order so the quadratic cannot return unnoticed. The refusal pin: a probe once printed cosines from hash pseudo-embeddings against a dead daemon with no indication. The four embedding scripts and the separation scorer carry the discipline; the older scripts predate it.

**5. A default may not impersonate a measurement.** An aborted maintenance cycle reports its counts as unknown, not zero, with the comment beside it: an empty mapping "would read as 'nothing was refused', which is the same claim `0` made. An aborted cycle did not count." Gate refusals are declared on the `done` frame with their rule names rather than dropped. Declared and recorded are different claims, and the constitution now states the line: every refusal is declared on the response; a refusal of a well-formed request for a governed act is also recorded; a request that was never valid is declared only. The embedding layer's fallback counter is monotone for the life of the process; recovery clears the degraded flag and deliberately not the count, because "a counter a recovery can reset cannot answer 'was anything I computed built on a fallback vector'." The rule was written after a cycle's abort path built its result from dataclass defaults, a promoted-count of zero read as "ran and promoted none", and a recorded investigation drew a conclusion from it. The rule now has two siblings in the constitution, found the same way — by catching the defect happening: a false signal is not removed without the true one taking its place (no false blank), and a claimed feature is not retired as a side effect of a decision about something else (no silent subtraction). The three forbid the same thing from three sides: the system saying something its behaviour does not support. The surfaces still outside the first rule are listed in §7; the second was written after a retirement in this project left a rendered field empty; the third after a claim was reasoned away inside a packet about the halt.

**Guards born of incidents.** Most of the structural guards exist because something specific broke, and the origin is recorded beside each one: a deduplication pass wrote a tier value outside the schema by direct SQL and killed the scheduler and every turn whose retrieval touched the row — archival is a status column, not a tier, because of it; importing a helper module migrated the operator's live store — import purity; an event was renamed at one end of the stream and not the other — the three-way contract reconciliation; a threshold shipped above both measured signals — the no-override pin. The estate is reactive and says so. What an assessor gains from that is a guard set whose every member has a failure it can be checked against.

**Conventional parts, and where they are not.** Hash chaining is hand-rolled sha256 over canonical block fields linked by previous hash, with a Merkle root per block over the records it seals since W8 and an Ed25519 signature per block since W9; a missing snapshot is sealed into the hash as an absence, and later-added block fields are hashed only when non-default so earlier hashes recompute unchanged. Spreading activation is a breadth-first pass with per-hop attenuation, plus a per-edge transmission refractory and column-based lateral inhibition. Hebbian movement is capped-increment with long-term depression, modulated by prediction error. Tiered storage is hand-rolled over SQLite, and its one non-textbook property is the one most of the guards above protect: **decay is a read-time projection and never a write.** Stored values are monotone; the entire prominence layer is computed at read from the stored value, elapsed time, the source's arrival discount and the sum of recorded adjustments. The recalibration module states the consequence in one line — "Learning happens inside the audit trail rather than beside it" — and the edge module states the other invariant that follows: "Law I: edges are potentials, not facts." An edge weight says how much signal reaches the target when the source fires, not that anything is true.

## 9. Relation to Zep's Graphiti

The nearest published design is Graphiti, the temporal knowledge-graph engine
behind Zep's memory layer (arXiv:2501.13956; open source, Neo4j or FalkorDB
backends). An assessor who knows it will ask what is different and why, so the
comparison is made here rather than left to inference. **It is a comparison of
purpose and of the design choices that follow from purpose, not a claim of
superiority** — Graphiti is a mature project operating at a scale this system
has not reached as yet.

**What is shared.** Both store facts as subject–relation–object edges with a
source and time; both ingest continuously from conversation and structured data
without batch recomputation; both use several retrieval channels; both retain
superseded facts rather than deleting them.

**What Graphiti is for.** Correct, current answers for an agent. Its central
mechanism is a bi-temporal model: every fact carries when it was true in the
world and when the system learned it, so a query can ask what was true on a
date. When new information conflicts with old, Graphiti uses the temporal
metadata to invalidate the superseded edge — marked invalid, not discarded — and
it consistently prioritises new information. Extraction, entity resolution and
deduplication are LLM-driven and autonomous; communities are maintained by label
propagation. It is evaluated on memory-retrieval benchmarks.

**Its graph accumulates and reorganises rather than calibrates.** Structure
adapts as data arrives — entities merge, communities recompute, superseded edges
are invalidated. **Nothing in Graphiti's published material seems to describe a
confidence per fact that moves in response to what happened downstream**, nor an
association that forms because two things keep appearing together. Its temporal
metadata records when a fact became or stopped being true, not how well
supported it is.

**What NEXUS is for.** An answer to a different question: not what is true now,
but what the system believed when it answered, what it drew on, and what it left
out — answerable afterwards, from a sealed record, by someone who was not there.
**Six design choices follow from that purpose, and each is where the two
systems diverge.**

**1 · Contradiction is retained, not resolved.**

Graphiti resolves conflict by temporal supersession, which is the right rule
when the newest fact is usually the truest. In an evidence-record use the newest
claim is not privileged: which side was right is a judgement someone must own.
So both sides stay retrievable, the conflict is surfaced to the client and
recorded in lineage, and resolution is a recorded human act — archival or an
outcome event — never automatic.

**2 · Transaction time only, by the same principle.**

Bi-temporal modelling carries two axes: **valid time**, when a fact was true in
the world, and **transaction time**, when the system held, learned or judged
something.

**Valid time requires invalidation** — deciding a world-truth window for a fact
is resolution by another name — and Graphiti needs bi-temporal edges because it
invalidates. **Transaction time requires none.**

This design takes the second axis completely: when a claim arrived, what it was
worth at each answer it entered, when its standing was adjusted and by whom. And
it must never manage the first, for the reason in item 1. What is true now is a
question for the reader of the record, not a field in it — **so this needs a
query where Graphiti needs an edge.**

The two numbers the store keeps, prominence as a read-time projection and the
monotone high-water record, are both transaction-time facts about the system's
own trust. The weight at injection is frozen per answer in
lineage, which per-fact provenance has no way to express.

**3 · Retrieval is ordered by standing, not by similarity — and provenance is a discount within standing.**

**Both systems retrieve; the difference is what decides rank.**

Here, terms are matched lexically and the question is compared by meaning
against every indexed claim, and both feed one candidate pool. **Similarity
decides whether a claim is considered. It never decides where it ranks** — if it
could, a model's own paraphrase would outrank a person's stated fact by being
worded more like the question. Similarity is therefore kept out of the sort entirely, and a static check fails the build if it appears there. What decides rank is standing: tier, then prominence scaled by evidence class. Provenance is a discount, not a strict first key, so an extraction-class claim with high prominence can outrank a human-asserted one of lower prominence in the same band; the record layer is contained (a re-assertion cannot cross classes) and the read side is not class-first. Earlier revisions of this section said "ordered by provenance"; that overstated.

**Measured against a real store:** thirty questions, of which lexical matching
alone answers 26 and the union answers 30. Six control questions on subjects the
store knows nothing about correctly return nothing — **and the controls, not a
chosen value, set the similarity threshold.** At a looser setting one control
leaked.

Graphiti's retrieval is graph traversal and semantic search over an
LLM-maintained ontology, at a scale this store has not been tested at as yet. **Neither
has been benchmarked against the other**, and the two are optimising different
things: recall of the current truth, against a ranking that a reader can later
justify.

**4 · The unit of provenance is the answer, not the fact.**

Graphiti records which episode produced each fact. NEXUS records, per answer,
the full injected set with weights at injection, which were cited, what
contradicted them, what was refused at extraction, and a pre-retrieval forecast
scored against a null — hashed and chained.

**5 · Learning is calibration, and it is bounded.**

Two mechanisms, and neither has a counterpart in a memory layer because neither
is needed to answer *what is true now*.

**Association strengthens with co-activation and fades without it.** Terms that
appear together in a turn strengthen their link; unused links weaken; a link
becomes durable only if it recurs across separated occasions, so the scaffolding
of one working session is distinguished from knowledge that returns over weeks.
**Nothing curates this** — it is a picture of what the organisation actually
asks about, built from what it actually asked. **(On the reference instance, learning is
frozen since 2026-10-01 until the recurrence fix lands; see §7.)** **Its output shapes what comes to
mind; it is not a claim anyone made**, and keeping those two things distinct is
an open question recorded in §7 rather than a settled boundary.

**And confidence moves when an outcome arrives.** Not when new data supersedes
old — **when a decision the answer contributed to is recorded as approved,
reworked or rejected.** The movement is bounded by a policy someone installed,
attributed to whoever caused it, and sealed alongside the rule that permitted
it. Refusals are recorded before the error is raised, so a declined adjustment
cannot be made to disappear.

**Every learning system adjusts confidence by overwriting; that is what training
is.** Here the stored value never moves — an adjustment is a separate recorded
event, which is what makes the adaptation inspectable rather than merely
present.

**6 · Nothing is autonomous past the admission gate.**

Graphiti's ingestion, resolution and invalidation run without confirmation,
which is what a memory layer needs. Here extraction passes a gate that refuses
and declares; deduplication proposes and a human confirms; the background
process may only propose; every governance act is actor-stamped. **The cost is
throughput; the benefit is that no state of consequence changes without a
recorded decision.**

**What NEXUS has that Graphiti does not aim at.** The sealed lineage and archive
chain; the citation forecast and calibration ledger, which measure the system's
knowledge of its own retrieval; refusals as declared output; and the guard
estate of §5. **A memory layer needs none of these**, which is the point rather
than a criticism. **The duplicates this store retains by design (§3) are exactly
what Graphiti's resolution would merge** — and whether that is a strength
depends entirely on whether anyone has to defend the record later.

**Why not build on it.** The record layer is orthogonal to the store beneath it
and could in principle sit over a Graphiti graph; this has not been tried. It
was not tried because two of Graphiti's defining behaviours — automatic
invalidation on conflict, and automatic entity merging — are the two things the
record layer must not allow to happen without a recorded decision, and switching
them off removes most of what Graphiti is for.

**The store here is smaller and simpler because the design's weight is in the
record.** That is a choice about where the difficulty belongs, not an admission
about the retrieval.

## 10. The intended cloud build — design, partly built

**Status of this section: intended, but for three parts built since it was written.** The container image, compose profiles and a fresh host from cloud-init (W3), the Postgres store (W3b), and identity from a proxy in front with one process per tester (W4) are built (`docs/DEPLOY.md`); replicas, a scheduler across them, a shared session graph and object storage are not, and the table's gap column below is unchanged. The compaction-boundary audit and the v3.1 Phase 0 investigation both looked for the components the enterprise briefing names — a gateway policy, a validated identity provider, a container platform, a relational store, an event bus, a metrics sink — and found none of them in code. This section exists because an assessor will ask what the cloud build is, and because the honest answer is not a diagram of services but a list of what the sections above *require* of any deployment that replicates the process, shares the store and puts a real identity on the wire. Each requirement below is derived from a numbered section; each gap is stated as a gap. Service names are the ones the v3.1 delta specification uses; nothing here depends on the vendor.

The rule that governs the section: **every change the cloud build makes must leave the local single-process path byte-identical**, because the local path is the reference implementation and the only one the guard estate has been proven against. The record layer's semantics are portable by construction — they are properties of tables and hashes, not of a process — and the cloud work is topology around them.

### 10.1 The intended topology

An **interceptor on the inference path.** The organisation's application does not call NEXUS; it calls its model endpoint as before, and a gateway policy routes that call through NEXUS. NEXUS assembles the prompt from its store, streams the answer back, and writes the lineage record. The briefing's phrase for this is *one gateway policy, no application changes*. That is true of the wedge — an answer with a sealed record, from day one, for an application that does not know NEXUS exists — and false of anything past it: attribution (§10.4, work units) needs the application to say what it is working on, which is a header at minimum, and the delta specification says so. The v3.1 review's reading is kept here: **the interceptor is the wedge, not the destination.** A buyer who deploys the wedge expecting the destination has bought a memory of what the model attended to, not a memory of what the organisation decided.

Figure 5 draws the intended shape. Read it beside Figure 1: every box on the left of Figure 1 survives; the four stores become one relational store plus object storage; the scheduler becomes a singleton; a gateway and an event bus are added at the edges; nothing is added to the record layer's semantics.

### 10.3 What the cloud build must not change

These are the properties the record layer is for; a deployment that loses one has not deployed NEXUS. From §8 and §9, in one list: similarity never ranks; the forecast is committed before retrieval and cannot see it; the record layer cannot leak into the prominence layer through a read; pins fail in both directions; measurements are guarded against measuring themselves; a default never impersonates a measurement, a false signal is never removed without its replacement, a claimed feature is never retired as a side effect; contradiction is retained and resolution is a recorded human act; nothing is autonomous past the admission gate; every state change of consequence waits for a confirmed, actor-stamped act; the archive has one writer; nothing is deleted. And one from the delta specification, which this document adopts as a constraint on any consumer: **a governance layer above NEXUS reads it and never writes it, and nothing it computes enters the model's context.**

### 10.4 What the organisational layer adds, in order

The delta specification asks for seven changes; the review kept two as load-bearing and reshaped both against the code. The order is the queue's order, and every phase is built and proven locally first, because principle 7 of the specification — both deployments — is satisfied by building on the reference path and porting the topology, not by building twice.

1. **Work-unit attribution** (Phase 1, **built**): a `work_unit` table, an append-only junction from claims to the units that admitted them, and attribution fields on the lineage record. No retrieval change — that is Phase 4, and it ships only if a pre-registered measurement moves. The application supplies the unit and the accountable identity as **body fields**; absent both, a session pseudo-unit, reported separately as unattributed. History is unattributed by absence — nothing sealed is rewritten, and a record that predates the fields hashes unchanged. **What the drafted version had and the built one does not:** a governed open-and-close route, a server-side lifecycle, a one-open-unit rule, and a header path. All four were withdrawn on one observation — a work unit is the scope label with a row and a junction, and attaching a label changes no standing, so there is nothing for a gate to govern. **One exposure is recorded rather than gated:** a caller can create unbounded unit rows by sending fresh ids, as it can send unbounded scopes, and the session pseudo-unit adds one row per session where scope's absence is a single shared literal. A declared count is the eventual answer; there is no gate and the growth is not yet recorded.
2. **Decision fields on the lineage record** (Phase 2, **built**, W6): envelope version, flags, confirmation reference, decision boundary and who asserted it, and the forecast's per-turn score and null persisted — closing the §8 limitation that they live only on the `done` frame. A work-unit close is a governance record listing the unit's lineage ids, not a copy of them.
3. **Merkle root and inclusion proofs** (Phase 3, **built**, W8): the cycle's snapshot block gains a root over the lineage hashes it seals, hashed only when non-default so earlier blocks recompute unchanged; a read route returns a record's proof. This is the cloud build's one record-layer requirement.
4. **The retrieval boost for an open unit** (Phase 4): a rank change, so it is measured against the thirty-question set and the forecast's null before it ships, and it does not ship if it moves no measured number.
5. Accountable identity, policy invariants at the confirm gates and refusal ledger (not in the integrity check, which has no hold semantics and now no halt), role routing, the shared curated tier, and the value-stream ledger — each an extension of an existing primitive, each with a register line, each after the four above.

### 10.5 What is open, and would be open on any topology

Scale: the store has never been tested past tens of thousands of claims, and the growth-order guards give the shape of cost, not its value. Concurrency: the loop's frozen state is replaced atomically per turn in one process; the same discipline across replicas is a design, not a test. Per-turn rehydration cost: unmeasured. The citation flag: ~22% under-report, inherited by reinforcement, the archival exemption and the forecast's scoring, and by any attribution that reads "cited". Curiosity: dark. The cascade: tiers 1–3 free nothing within the turn; their next-turn effect unmeasured. Compaction fidelity: listed, not measured. Groupthink and poisoning through a shared tier: mitigated by human-only writes and sealed provenance, not eliminated, and the specification says so. Goodhart on any published ledger metric: present from the day the metric is reported, and the only defence is components-not-composites plus the fact that loosening a rule is itself a sealed record. No benchmark against any other system, and none claimed.

The cloud build inherits every one of these. It resolves none of them, and a deployment plan that implies otherwise should be read against this list.

## 11. How to falsify this document

Every load-bearing claim above is checkable from a checkout, without trusting the prose. The fastest routes, for a skeptical reader:

- **The event contract (§2, §5):** run `tests/test_sse_contract.py`. It reconciles the declared event list against what the code can emit and what the frontends bind, with the known gaps pinned. If this document's request-path story were wrong, this file is where it breaks.
- **The auth and route posture (§6, §7):** run `tests/test_auth_coverage.py` and `tests/test_bind_conditional_routes.py`. The first derives the writer set from the live router and exercises three token cases per writer; the second forces every read route to be either explicitly open-with-reason or actually gated. An endpoint this document forgot would fail there, not here.
- **The chokepoint and single-writer claims (§3):** run `tests/test_extraction_gate.py` (the ingest-route enumeration) and `tests/test_governed_adaptation.py` (the stored-weight single-writer guard). The caller pins on the dangerous primitives live in `tests/test_budget_report.py`, `tests/test_archival_ledger.py` and `tests/test_weight_restoration.py` — add a rogue caller anywhere and the build fails.
- **The seals (§3, §4):** with a running instance, `GET /lineage/verify` and `GET /governance/verify` recompute every sealed record against the chain and report failures by layer — content edit, seal mismatch, or chain break — rather than a boolean. Rewrite any sealed row by hand and run them again.
- **The measurement claims (§7):** the scripts under `scripts/` (`measure_retrieval.py`, `consolidation_feedback.py`, `measure_cycle_cost.py` and siblings) reproduce the numbers this project's records quote, print the store's checksum before and after, and abort by name rather than degrade — several refuse to run at all if their inputs would make the result noise.
- **The guard estate's own coverage (§5):** run `scripts/guard_estate_census.py` against the checkout; it lists every structural guard with whether it has a companion and what the companion plants. The 27-of-135 figure in §5 should reproduce, and any guard this document leans on can be looked up by name.
- **The attribution claims (§3, §6, §10.4):** a fixture conversation's request hash is committed from the pre-change tree and asserted identical turn by turn, so *no retrieval change* is a byte comparison and not a promise; a two-unit fixture prints both rows and both junction rows for a claim re-asserted under the same source and under a different one; a route-level test sends the `X-Nexus-*` headers beside the body and asserts the headers name nothing; and a two-turn test asserts the second turn inherits no unit. The schema guard over `triples` now covers the two new tables and the lineage record in the same two-layer shape, so a column arrives only with a recorded reason.
- **The compaction claims (§2, §5):** run `tests/test_bd3_halt_retired.py` — its guard fails on any code under `backend/` that assigns, compares or branches on a `corrupted` attribute, and its behavioural test forces micro on a synthetic rig and asserts the WARN report and a completed turn. `tests/test_stream_truncation.py::test_a_healthy_turn_delivers_done` is the pin that `done` is the final frame.
- **The schema claim (§5):** `tests/test_scope_recorded.py` carries the two-layer `triples` guard; plant a column on a copy of the DDL without answering for it and the build fails naming OQ-12.
- **The cloud build (§10):** nothing to run. The checkout contains no gateway, identity, container, relational-store or bus code, and any claim that it does is false as of this revision. §10.2's gap column is the falsification list: each row becomes a test when it is built, and a build that closes a row without one has skipped the discipline the rest of this document describes.
- **Everything at once:** the full suite. It is the ~2,000 tests counted in §5, and the structural guards described there fail loudly and name what moved — with the census's caveat that a guard without a companion is a claim, not a proof.
